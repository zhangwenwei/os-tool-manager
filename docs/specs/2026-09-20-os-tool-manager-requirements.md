## 0. 记法

本文档第 3、4、5 章的全部要件依据 EARS 记述。EARS 将要件限定为以下五种句型，以排除歧义并保证可验证性。

| 句型 | 结构 | 适用场合 |
|---|---|---|
| 普遍性 (Ubiquitous) | 系统应当〈响应〉。 | 恒常成立的性质 |
| 事件驱动 (Event-driven) | 当〈触发〉时，系统应当〈响应〉。 | 由离散事件触发 |
| 状态驱动 (State-driven) | 在〈状态〉期间，系统应当〈响应〉。 | 某状态持续中恒常成立 |
| 异常处理 (Unwanted) | 如果〈条件〉，则系统应当〈响应〉。 | 异常、错误、非期望输入 |
| 可选特性 (Optional) | 若〈具备特性〉，系统应当〈响应〉。 | 仅部分构成下成立 |
| 复合 (Complex) | 上述句型的组合。 | 需同时限定状态与事件 |

本文档中「系统」一律指 os-tool-manager 本体（服务端与前端的总体）。各要件的句型在「型」列中标示。

## 1. 概要

### 1.1 目的

在 macOS 上提供一个本地 Web 面板，用于查看和管理开发环境中的命令行工具与运行时版本，替代反复敲命令、记不住包名和版本的手工操作。

### 1.2 背景

使用者在多台 Mac 上工作，各台机器安装的工具与版本不一致。需要一个在任意一台机器上打开就能看清「这台装了什么、版本多少、哪些该更新」的入口，并能直接执行更新与卸载。

### 1.3 利用者

仅制作者本人。不存在多用户、权限分级、账号体系的需求。

### 1.4 利用形态

- 同一份代码通过 Git 分发到本人的多台 Mac
- 每台机器各自在本地启动服务，只管理本机
- 机器之间互不感知，无网络互通需求

### 1.5 典型场景

1. 新配置一台 Mac，想知道常用工具装齐了没有
2. 想批量确认哪些 Homebrew 包有更新，并选择性更新
3. 想清理不再使用的包，释放磁盘
4. 想确认当前生效的 Node / Python 版本，以及装了哪些版本

## 2. 范围

### 2.1 对象范围（第一版）

| ID | 对象 | 说明 |
|---|---|---|
| SC-01 | Homebrew | formula 与 cask 的安装列表、版本、更新、卸载 |
| SC-02 | Node 版本管理 | nvm 管理的版本列表、当前生效版本 |
| SC-03 | Python 版本管理 | pyenv 管理的版本列表、当前生效版本 |

### 2.2 对象外范围

以下内容明确不在第一版实现，且部分为永久性不做，记录于此以防范围膨胀。

| ID | 对象外项目 | 理由 |
|---|---|---|
| OUT-01 | 系统状态监控（CPU / 内存 / 磁盘 / 进程） | 与 macOS 活动监视器功能重复 |
| OUT-02 | 任意命令输入执行 | 风险与收益不成比例，永久不做 |
| OUT-03 | 多机集中管理、远程访问 | 采用单机自治方针，永久不做 |
| OUT-04 | 用户账号与权限体系 | 仅本人使用，无必要 |
| OUT-05 | 定时任务、后台自动刷新 | 采用打开页面时拉取的方针 |
| OUT-06 | Docker 容器管理 | 延至第二版，通过适配器接口接入 |
| OUT-07 | 端口占用查看与进程终止 | 延至第二版，通过适配器接口接入 |
| OUT-08 | sudo 提权操作 | 安全方针，永久不做 |

## 3. 功能要件

### 3.1 生态探测

| ID | 型 | 要件 |
|---|---|---|
| FR-01 | 事件驱动 | 当系统接收到生态一览取得请求时，系统应当对全部已注册的适配器执行探测处理。 |
| FR-02 | 异常处理 | 如果某适配器的探测处理返回不可用，则系统应当将该生态从一览中排除，且不生成错误通知。 |
| FR-03 | 异常处理 | 如果某适配器的探测处理抛出异常，则系统应当将该生态视为不可用，且不影响其他适配器的探测。 |

> FR-02 的理由：使用者的多台机器环境本就不一致，「未安装」是常态而非异常状态。

### 3.2 一览显示

| ID | 型 | 要件 |
|---|---|---|
| FR-04 | 普遍性 | 系统应当按生态分卡片显示条目一览。 |
| FR-05 | 普遍性 | 系统应当为一览中的每个条目显示名称、当前版本、最新版本与状态。 |
| FR-06 | 普遍性 | 系统应当将条目状态表示为 `ok`、`outdated`、`unknown` 三者之一。 |
| FR-07 | 异常处理 | 如果无法取得某条目的最新版本，则系统应当将该条目状态置为 `unknown`，且最新版本显示为未知。 |
| FR-08 | 事件驱动 | 当页面加载完成时，系统应当对全部可用生态并发发起一览取得请求。 |
| FR-09 | 状态驱动 | 在某生态的一览取得处理进行期间，系统应当仅在该生态的卡片内显示加载状态，并保持其他卡片的显示与操作不受影响。 |
| FR-10 | 事件驱动 | 当使用者点击某卡片的刷新按钮时，系统应当仅重新取得该生态的一览。 |
| FR-11 | 可选特性 | 若生态具备「当前生效版本」的概念，系统应当在该生态的卡片中标示当前生效的版本。 |

> FR-08、FR-09 的理由：Homebrew 相关命令需数秒至数十秒且依赖网络，不得因此阻塞其他生态的显示。

> FR-11 的适用范围：SC-02（Node）与 SC-03（Python）适用，SC-01（Homebrew）不适用。

### 3.3 操作执行

| ID | 型 | 要件 |
|---|---|---|
| FR-12 | 普遍性 | 系统应当依据条目的 `actions` 字段动态渲染该条目可用的操作按钮。 |
| FR-13 | 事件驱动 | 当使用者请求执行非破坏性操作时，系统应当直接执行该操作。 |
| FR-14 | 复合 | 当使用者请求执行破坏性操作时，系统应当要求二次确认；仅在取得确认后，系统应当执行该操作。 |
| FR-15 | 状态驱动 | 在某操作执行期间，系统应当在对应卡片显示执行中状态，并禁用该条目的全部操作按钮。 |
| FR-16 | 事件驱动 | 当操作正常结束时，系统应当自动重新取得该生态的一览。 |
| FR-17 | 异常处理 | 如果操作以失败结束，则系统应当显示该命令的原始输出，且不得代之以无具体内容的失败提示。 |

> FR-12 的理由：并非所有生态都支持全部操作。nvm / pyenv 的版本条目不存在「原地更新」的概念，仅提供卸载。界面不得假定操作集合固定。

> FR-17 的理由：「操作失败」一类无信息量的提示无法支撑排查，必须暴露原始输出。输出量的上限依 NFR-07。

### 3.4 数据取得方针

| ID | 型 | 要件 |
|---|---|---|
| FR-18 | 事件驱动 | 当页面打开时，系统应当执行实际命令取得数据。 |
| FR-19 | 普遍性 | 系统不应当将既存的取得结果用于界面显示。 |

> FR-19 的补充：SEC-06 所需的条目 ID 集合是唯一例外，该集合仅用于安全校验，不用于显示。

## 4. 非功能要件

| ID | 型 | 要件 |
|---|---|---|
| NFR-01 | 普遍性 | 系统应当在 macOS 与 Node.js 20 以上的环境中运行。 |
| NFR-02 | 普遍性 | 系统应当仅使用 Node.js 标准库实现，不应当引入任何第三方运行时依赖。 |
| NFR-03 | 事件驱动 | 当使用者在新机器上克隆本仓库后，系统应当无需执行依赖安装即可启动。 |
| NFR-04 | 普遍性 | 系统应当可通过 `npm start` 启动。 |
| NFR-05 | 普遍性 | 系统应当从 `.env` 读取机器固有配置（超时时长、端口固定与否）。 |
| NFR-06 | 异常处理 | 如果子进程的执行时间超过配置的超时值（默认 60 秒），则系统应当终止该子进程并返回超时错误。 |
| NFR-07 | 异常处理 | 如果子进程的输出超过配置的上限，则系统应当截断该输出并保留首尾部分。 |
| NFR-08 | 普遍性 | 系统应当将生态固有的知识完全封装于适配器模块内，路由层与前端不应当包含任何具体生态的名称。 |
| NFR-09 | 事件驱动 | 当追加新生态时，系统应当仅通过新增适配器文件与注册来支持该生态，不应当要求修改路由层与前端。 |

> NFR-02 的理由：零依赖使换机成本降为零，同时排除供应链风险。本面板界面复杂度低，原生实现足够。

> NFR-08、NFR-09 为同一设计方针的两面：前者是恒常性的结构约束，后者是扩展时的可验证条件。

## 5. 安全要件

本面板可执行卸载等破坏性操作。以下要件全部为必须项，不接受以「仅本人使用」为由的妥协。

| ID | 型 | 要件 |
|---|---|---|
| SEC-01 | 普遍性 | 系统应当仅将 HTTP 服务绑定至 `127.0.0.1`，不应当绑定至 `0.0.0.0` 或任何外部可达地址。 |
| SEC-02 | 事件驱动 | 当服务启动时，系统应当生成随机端口与随机访问令牌。 |
| SEC-03 | 异常处理 | 如果请求未携带有效的访问令牌，则系统应当拒绝该请求。 |
| SEC-04 | 异常处理 | 如果 POST 请求的 `Origin` 头与本服务的地址不一致，则系统应当拒绝该请求。 |
| SEC-05 | 异常处理 | 如果请求指定的操作种类未在对应适配器中声明，则系统应当拒绝该请求。 |
| SEC-06 | 异常处理 | 如果请求指定的条目 ID 不存在于该生态最近一次一览取得的结果中，则系统应当拒绝该请求，并提示使用者先刷新一览。 |
| SEC-07 | 普遍性 | 系统应当将命令与参数以数组形式传递给子进程，不应当经由 shell 拼接字符串。 |
| SEC-08 | 异常处理 | 如果破坏性操作的请求体未携带确认标记，则系统应当拒绝该请求。 |
| SEC-09 | 普遍性 | 系统不应当使用 `sudo`，也不应当提供任何提权入口。 |

> SEC-01 的理由：服务若绑定至外部可达地址，同一局域网内的第三方即可访问具备破坏性操作能力的面板。

> SEC-04 的理由：浏览器的同源策略无法阻止跨站发出的写请求。使用者浏览其他网页时，恶意页面可向本地服务发送请求，`Origin` 校验是此处的必要防线。

> SEC-06 的实现前提：服务端在内存中保留各生态最近一次一览的条目 ID 集合，仅用于本项校验。服务重启后该集合为空，此时的操作请求将被拒绝，使用者需先刷新一览。

> SEC-07 与 SEC-05、SEC-06 构成命令注入的三重防线：操作种类白名单、操作对象白名单、无字符串拼接。

## 6. 架构设计

### 6.1 方针

采用适配器模式。各生态实现统一接口，路由层与前端仅依赖该统一接口，不持有任何具体生态知识（NFR-08）。

采用理由：第二版确定要追加 Docker 与端口管理（OUT-06、OUT-07）。适配器的抽象成本为一次性支出，而为各生态分别实现路由与界面的重复成本会在每次扩展时重复发生。此外探测处理（FR-01）天然覆盖「本机未安装该生态」的情形，契合多机环境不一致的实际状况。

### 6.2 目录构成

```
os-tool-manager/
├── server/
│   ├── index.js           启动入口，绑定 127.0.0.1，生成随机端口与令牌
│   ├── security.js        令牌校验、Origin 校验、白名单校验
│   ├── routes.js          统一 API 路由（不含生态知识）
│   ├── exec.js            子进程执行封装：超时、输出截断、错误归一化
│   └── adapters/
│       ├── registry.js    适配器注册表
│       ├── homebrew.js
│       ├── node.js
│       └── python.js
├── web/
│   ├── index.html
│   ├── app.js             渲染统一结构（不含生态知识）
│   └── style.css
├── docs/
│   └── specs/
└── .env                   机器固有配置（版本控制对象外）
```

### 6.3 模块边界

| 模块 | 职责 | 禁止事项 | 关联要件 |
|---|---|---|---|
| `routes.js` | 请求分发、适配器调用 | 不得出现具体生态名称 | NFR-08 |
| `web/app.js` | 渲染统一结构 | 不得出现具体生态名称 | NFR-08 |
| `adapters/*` | 封装单一生态的全部知识 | 不得直接操作 HTTP | NFR-09 |
| `exec.js` | 子进程执行 | 不得含业务判断 | NFR-06、NFR-07 |
| `security.js` | 安全校验 | 不得含业务判断 | SEC-03～SEC-08 |

## 7. 接口定义

### 7.1 适配器接口

```js
{
  id: 'homebrew',          // 唯一标识
  label: 'Homebrew',       // 显示名
  detect(),                // → boolean：本机是否可用（FR-01）
  list(),                  // → Item[]
  actions: {
    update:    { destructive: false, run(item) },
    uninstall: { destructive: true,  run(item) }
  }
}
```

### 7.2 条目结构 Item

```js
{
  id: 'ripgrep',           // 生态内唯一，SEC-06 的白名单比对对象
  name: 'ripgrep',         // 显示名
  current: '14.1.0',       // 当前版本
  latest: '14.1.1',        // 最新版本，无法取得时为 null（FR-07）
  status: 'outdated',      // ok | outdated | unknown（FR-06）
  actions: ['update', 'uninstall']   // 该条目可用的操作（FR-12）
}
```

### 7.3 API 端点

| 方法 | 路径 | 说明 | 关联要件 |
|---|---|---|---|
| GET | `/api/adapters` | 返回本机可用的生态一览 | FR-01～FR-03 |
| GET | `/api/adapters/:id/items` | 返回指定生态的条目一览 | FR-05～FR-07 |
| POST | `/api/adapters/:id/actions/:action` | 对指定条目执行操作 | FR-13～FR-17 |

## 8. 错误处理方针

基本原则：**降级、不崩溃、不静默**。

具体行为已在各章要件中规定，此处仅作汇总索引，不重复定义。

| 状况 | 处理 | 要件 |
|---|---|---|
| 探测失败或命令不存在 | 该生态从一览排除，不视为错误 | FR-02、FR-03 |
| 一览取得失败 | 仅该卡片显示错误与重试手段，不影响其他卡片 | ERR-01 |
| 最新版本无法取得 | 状态置为 `unknown` | FR-07 |
| 子进程超时 | 终止进程并返回超时错误 | NFR-06 |
| 输出过大 | 截断并保留首尾 | NFR-07 |
| 操作失败 | 显示命令原始输出 | FR-17 |

上表中仅此一项为本章新增要件：

| ID | 型 | 要件 |
|---|---|---|
| ERR-01 | 异常处理 | 如果某生态的一览取得失败，则系统应当在该生态的卡片内显示错误信息、标准错误输出的摘要与重试手段，并保持其他卡片的显示不受影响。 |

## 9. 测试方针

### 9.1 可测性设计

各适配器须将「执行命令」与「解析输出」分离，解析部分实现为纯函数，使测试不依赖本机实际安装状态。

```js
function parseBrewList(stdout) { ... }        // 纯函数，单元测试对象
async function list() { return parseBrewList(await exec(...)); }
```

### 9.2 测试对象与对应要件

| 对象 | 内容 | 验证要件 |
|---|---|---|
| 解析函数 | 以实际命令输出样本为输入，覆盖正常、空列表、格式异常三种情形 | FR-05～FR-07 |
| `security.js` | 令牌校验、Origin 校验、操作白名单、对象白名单、确认标记校验 | SEC-03～SEC-08 |
| `exec.js` | 超时时子进程确实被终止、输出截断行为 | NFR-06、NFR-07 |
| 路由层 | 注入伪适配器验证 API 契约，不触碰实际系统 | FR-01～FR-03、NFR-08 |

### 9.3 测试对象外

实际执行 `brew upgrade` 等命令的端到端测试。理由：耗时、有副作用、依赖环境。以手动验证替代。

### 9.4 测试框架

Node.js 内置 `node:test`。遵循 NFR-02 的零依赖方针。

## 11. 用语

| 用语 | 说明 |
|---|---|
| 系统 | os-tool-manager 本体（服务端与前端的总体） |
| 生态 | 一个工具管理体系，如 Homebrew、nvm、pyenv |
| 适配器 | 封装单一生态知识、实现统一接口的模块 |
| 条目 | 生态内的一个管理单位，如一个 Homebrew 包、一个 Node 版本 |
| 破坏性操作 | `destructive: true` 的操作。卸载、删除等不可轻易撤销的操作 |
| 探测处理 | 适配器的 `detect()`，判定该生态在本机是否可用 |
