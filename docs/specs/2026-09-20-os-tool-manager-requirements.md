## 1. 概要

### 1.1 目的

在 macOS 上提供一个本地 Web 面板，用于查看和管理开发环境中的命令行工具与运行时版本，替代反复敲命令、记不住包名和版本的手工操作。

### 1.2 背景

使用者在多台 Mac 上工作，各台机器安装的工具与版本不一致。需要一个在任意一台机器上打开就能看清「这台装了什么、版本多少、哪些该更新」的入口，并能直接执行更新与卸载。

### 1.3 利用者

仅制作者本人。不存在多用户、权限分级、账号体系的需求。

### 1.4 利用形态

- 同一份代码通过 Git 分发到本人的多台 Mac
- 每台机器各自在本地启动服务，只管理本机
- 机器之间互不感知，无网络互通需求

### 1.5 典型场景

1. 新配置一台 Mac，想知道常用工具装齐了没有
2. 想批量确认哪些 Homebrew 包有更新，并选择性更新
3. 想清理不再使用的包，释放磁盘
4. 想确认当前生效的 Node / Python 版本，以及装了哪些版本

## 2. 范围

### 2.1 对象范围（第一版）

| ID | 对象 | 说明 |
|---|---|---|
| SC-01 | Homebrew | formula 与 cask 的安装列表、版本、更新、卸载 |
| SC-02 | Node 版本管理 | nvm 管理的版本列表、当前生效版本 |
| SC-03 | Python 版本管理 | pyenv 管理的版本列表、当前生效版本 |

### 2.2 对象外范围

以下内容明确不在第一版实现，且部分为永久性不做，记录于此以防范围膨胀。

| ID | 对象外项目 | 理由 |
|---|---|---|
| OUT-01 | 系统状态监控（CPU / 内存 / 磁盘 / 进程） | 与 macOS 活动监视器功能重复 |
| OUT-02 | 任意命令输入执行 | 风险与收益不成比例，永久不做 |
| OUT-03 | 多机集中管理、远程访问 | 采用单机自治方针，永久不做 |
| OUT-04 | 用户账号与权限体系 | 仅本人使用，无必要 |
| OUT-05 | 定时任务、后台自动刷新 | 采用打开页面时拉取的方针 |
| OUT-06 | Docker 容器管理 | 延至第二版，通过适配器接口接入 |
| OUT-07 | 端口占用查看与进程终止 | 延至第二版，通过适配器接口接入 |
| OUT-08 | sudo 提权操作 | 安全方针，永久不做 |

## 3. 功能要件

### 3.1 生态探测

| ID | 要件 | 优先级 |
|---|---|---|
| FR-01 | 启动时探测本机安装了哪些对象生态 | 必须 |
| FR-02 | 未安装的生态不在界面显示，不视为错误 | 必须 |

> FR-02 的理由：使用者的多台机器环境本就不一致，「未安装」是常态而非异常状态。

### 3.2 一览显示

| ID | 要件 | 优先级 |
|---|---|---|
| FR-03 | 按生态分卡片显示条目一览 | 必须 |
| FR-04 | 每个条目显示：名称、当前版本、最新版本、状态 | 必须 |
| FR-05 | 状态区分 `ok`（最新） / `outdated`（有更新） / `unknown`（无法判定） | 必须 |
| FR-06 | 各卡片独立异步加载，互不阻塞 | 必须 |
| FR-07 | 各卡片提供独立的手动刷新按钮 | 必须 |
| FR-08 | Node / Python 卡片标示当前生效版本 | 必须 |

> FR-06 的理由：Homebrew 相关命令需数秒至数十秒且依赖网络，不得因此阻塞其他生态的显示。

### 3.3 操作执行

| ID | 要件 | 优先级 |
|---|---|---|
| FR-09 | 对条目执行「更新」操作 | 必须 |
| FR-10 | 对条目执行「卸载」操作 | 必须 |
| FR-11 | 破坏性操作执行前须二次确认 | 必须 |
| FR-12 | 操作执行中显示进行状态 | 必须 |
| FR-13 | 操作完成后自动重新拉取该生态的一览 | 必须 |
| FR-14 | 操作失败时完整显示命令原始输出 | 必须 |

> FR-09 / FR-10 补充：操作的可用性由各条目的 `actions` 字段逐条声明，并非所有生态都支持全部操作。例如 nvm / pyenv 的版本条目不存在「原地更新」的概念，仅提供卸载。界面须按 `actions` 字段动态渲染按钮，不得假定操作集合固定。

> FR-14 的理由：「操作失败」一类无信息量的提示无法支撑排查，必须暴露原始输出。

### 3.4 数据刷新方针

| ID | 要件 |
|---|---|
| FR-15 | 页面打开时自动拉取各生态的真实数据，不使用缓存 |
| FR-16 | 同时提供手动刷新，刷新粒度为单个生态 |

## 4. 非功能要件

| ID | 要件 | 内容 |
|---|---|---|
| NFR-01 | 运行环境 | macOS，Node.js 20 以上 |
| NFR-02 | 零运行时依赖 | 不使用任何第三方运行时包。HTTP 服务使用 Node 内置 `http`，前端使用原生 JavaScript |
| NFR-03 | 分发性 | `git clone` 后无需 `npm install` 即可启动 |
| NFR-04 | 启动方式 | `npm start` |
| NFR-05 | 环境依赖配置 | 机器相关配置（超时时长、是否固定端口）通过 `.env` 管理，不纳入版本控制 |
| NFR-06 | 命令超时 | 子进程执行默认超时 60 秒，可经 `.env` 调整 |
| NFR-07 | 输出保护 | 子进程输出超过上限时截断，保留首尾部分 |
| NFR-08 | 扩展性 | 新增生态仅需新增一个适配器文件并注册，不得修改路由层与前端 |

> NFR-02 的理由：零依赖使换机成本降为零，同时排除供应链风险。本面板界面复杂度低，原生实现足够。

## 5. 安全要件

本面板可执行卸载等破坏性操作，以下要件全部为必须项，不接受以「仅本人使用」为由的妥协。

| ID | 要件 | 内容 |
|---|---|---|
| SEC-01 | 监听地址限定 | 服务仅绑定 `127.0.0.1`，不得使用 `0.0.0.0`。防止同一局域网内的第三方访问 |
| SEC-02 | 随机端口与令牌 | 启动时生成随机端口与随机 token，token 经请求头校验 |
| SEC-03 | Origin 校验 | 所有 POST 请求校验 `Origin` 头，须与本服务地址一致。防止浏览中的恶意网页调用本地服务 |
| SEC-04 | 操作白名单 | 操作种类仅接受适配器中已声明的键名 |
| SEC-05 | 对象白名单 | 操作对象仅接受最近一次 `list()` 结果中存在的条目 ID，逐一比对 |
| SEC-06 | 无命令拼接 | 任何来自请求的字符串均不得拼入 shell 命令 |
| SEC-07 | 破坏性操作确认 | 破坏性操作的请求体须带确认标记，服务端二次校验 |
| SEC-08 | 禁止提权 | 不使用 `sudo`，不提供提权入口 |

> SEC-03 补充：浏览器的同源策略无法阻止跨站发出的写请求，Origin 校验是此处的必要防线。

> SEC-05 补充：服务端在内存中保留各生态最近一次 `list()` 的条目 ID 集合，仅用于本项校验。此保留不构成对 FR-15 的违反 —— 界面显示的数据始终来自实时拉取，该集合不用于显示。若操作对象不在集合内（例如服务重启后直接发起操作），返回错误并要求先刷新一览。

## 6. 架构设计

### 6.1 方针

采用适配器模式。各生态实现统一接口，路由层与前端仅依赖该统一接口，不持有任何具体生态知识。

采用理由：第二版确定要追加 Docker 与端口管理。适配器的抽象成本为一次性支出，而为各生态分别实现路由与界面的重复成本会在每次扩展时重复发生。此外 `detect()` 天然覆盖「本机未安装该生态」的情形，契合多机环境不一致的实际状况。

### 6.2 目录构成

```
os-tool-manager/
├── server/
│   ├── index.js           启动入口，绑定 127.0.0.1，生成随机端口与 token
│   ├── security.js        Origin 校验、token 校验、白名单校验
│   ├── routes.js          统一 API 路由（不含生态知识）
│   ├── exec.js            子进程执行封装：超时、输出截断、错误归一化
│   └── adapters/
│       ├── registry.js    适配器注册表
│       ├── homebrew.js
│       ├── node.js
│       └── python.js
├── web/
│   ├── index.html
│   ├── app.js             渲染统一结构（不含生态知识）
│   └── style.css
├── docs/
│   └── specs/
└── .env                   机器相关配置（版本控制对象外）
```

### 6.3 模块边界

| 模块 | 职责 | 禁止事项 |
|---|---|---|
| `routes.js` | 请求分发、调用适配器 | 不得出现具体生态名称 |
| `web/app.js` | 渲染统一结构 | 不得出现具体生态名称 |
| `adapters/*` | 封装单一生态的全部知识 | 不得直接操作 HTTP |
| `exec.js` | 子进程执行 | 不得含业务判断 |
| `security.js` | 安全校验 | 不得含业务判断 |

## 7. 接口定义

### 7.1 适配器接口

```js
{
  id: 'homebrew',          // 唯一标识
  label: 'Homebrew',       // 显示名
  detect(),                // → boolean：本机是否可用
  list(),                  // → Item[]
  actions: {
    update:    { destructive: false, run(item) },
    uninstall: { destructive: true,  run(item) }
  }
}
```

### 7.2 条目结构 Item

```js
{
  id: 'ripgrep',           // 生态内唯一，操作时的白名单比对对象
  name: 'ripgrep',         // 显示名
  current: '14.1.0',       // 当前版本
  latest: '14.1.1',        // 最新版本，无法取得时为 null
  status: 'outdated',      // ok | outdated | unknown
  actions: ['update', 'uninstall']   // 该条目可用的操作
}
```

### 7.3 API 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/adapters` | 返回本机可用的生态一览（执行各适配器的 `detect()`） |
| GET | `/api/adapters/:id/items` | 返回指定生态的条目一览 |
| POST | `/api/adapters/:id/actions/:action` | 对指定条目执行操作 |

## 8. 错误处理方针

基本原则：**降级、不崩溃、不静默**。

| 状况 | 处理 |
|---|---|
| `detect()` 失败或命令不存在 | 该生态不显示，不视为错误 |
| `list()` 失败 | 仅该卡片显示错误信息、stderr 摘要与重试按钮，其他卡片不受影响 |
| 子进程超时 | 终止进程，返回明确的超时错误 |
| 操作失败 | 完整显示命令原始输出 |
| 输出过大 | 截断并保留首尾，防止内存耗尽 |

## 9. 测试方针

### 9.1 可测性设计

各适配器须将「执行命令」与「解析输出」分离，解析部分实现为纯函数，使测试不依赖本机实际安装状态。

```js
function parseBrewList(stdout) { ... }        // 纯函数，单元测试对象
async function list() { return parseBrewList(await exec(...)); }
```

### 9.2 测试对象

| 对象 | 内容 |
|---|---|
| 解析函数 | 以实际命令输出样本为输入，覆盖正常、空列表、格式异常三种情形 |
| `security.js` | Origin 校验、token 校验、操作白名单、对象白名单。安全边界，必测 |
| `exec.js` | 超时时子进程确实被终止、输出截断行为 |
| 路由层 | 注入伪适配器验证 API 契约，不触碰实际系统 |

### 9.3 测试对象外

实际执行 `brew upgrade` 等命令的端到端测试。理由：耗时、有副作用、依赖环境。以手动验证替代。

### 9.4 测试框架

Node.js 内置 `node:test`。遵循 NFR-02 零依赖方针。

## 11. 用语

| 用语 | 说明 |
|---|---|
| 生态 | 一个工具管理体系，如 Homebrew、nvm、pyenv |
| 适配器 | 封装单一生态知识、实现统一接口的模块 |
| 条目 | 生态内的一个管理单位，如一个 Homebrew 包、一个 Node 版本 |
| 破坏性操作 | 卸载、删除等不可轻易撤销的操作 |
