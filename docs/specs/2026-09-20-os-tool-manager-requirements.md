## 0. 记法

本文档第 3、4、5、8 章的全部要件依据 EARS 记述。EARS 将要件限定为以下句型，以排除歧义并保证可验证性。

| 句型 | 结构 | 适用场合 |
|---|---|---|
| 普遍性 (Ubiquitous) | 系统应当〈响应〉。 | 恒常成立的性质 |
| 事件驱动 (Event-driven) | 当〈触发〉时，系统应当〈响应〉。 | 由离散事件触发 |
| 状态驱动 (State-driven) | 在〈状态〉期间，系统应当〈响应〉。 | 某状态持续中恒常成立 |
| 异常处理 (Unwanted) | 如果〈条件〉，则系统应当〈响应〉。 | 异常、错误、非期望输入 |
| 可选特性 (Optional) | 若〈具备特性〉，系统应当〈响应〉。 | 仅部分构成下成立 |

本文档中「系统」一律指 os-tool-manager 本体（服务端与前端的总体）。各要件的句型在「型」列中标示。

**助动词的使用**：肯定形统一用「应当」，否定形统一用「不应当」。第 6 章模块边界表中的「不得」为设计约束的表述，非要件。

## 1. 概要

### 1.1 目的

在 macOS 上提供一个本地 Web 面板，用于查看和管理开发环境中的包与工具，替代反复敲命令、记不住包名和版本的手工操作。

### 1.2 背景

使用者在多台 Mac 上工作，各台机器安装的工具与版本不一致。需要一个在任意一台机器上打开就能看清「这台装了什么、版本多少、哪些该更新」的入口，并能直接执行更新与卸载。

### 1.3 利用者

仅制作者本人。不存在多用户、权限分级、账号体系的需求。

### 1.4 利用形态

- 同一份代码通过 Git 分发到本人的多台 Mac
- 每台机器各自在本地启动服务，只管理本机
- 机器之间互不感知，无网络互通需求

### 1.5 典型场景

1. 想批量确认哪些 Homebrew 包有更新，并选择性更新
2. 想清理不再使用的包，释放磁盘
3. 想掌握系统 Python 的用户级包的全貌与版本
4. 新配置一台 Mac，想知道常用工具装齐了没有

## 2. 范围

### 2.1 对象范围（第一版）

| ID | 对象 | 说明 |
|---|---|---|
| SC-01 | Homebrew | formula 与 cask 的安装清单、版本、更新、卸载 |
| SC-02 | npm 全局包 | 全局安装包的清单、版本、更新、卸载 |
| SC-03 | uv 管理的 Python | uv 安装的 Python 版本的清单、当前生效标示、同小版本线内的更新、卸载 |

> 对象选定的依据：实机调查确认本机安装状况为 Homebrew（formula 39 件、cask 4 件）、npm 全局包 2 件。

> SC-03 的变更（v3.2）：原定的 pip 用户级包在本机恒为 0 件 —— 用户 site 目录不存在，面板上是一张永远空白的卡片。实机调查发现本机实际使用的是 uv（`~/.local/share/uv`），管理着一个 Python 3.11.16，而 uv 不受 Homebrew、npm、pip 任何一方管理。故将 SC-03 改为 uv。pip 适配器的实装保留于 git 历史，将来若在其他机器上有系统级 pip 包，可重新接入。

### 2.2 对象外范围

以下内容明确不在第一版实现，且部分为永久性不做，记录于此以防范围膨胀。

| ID | 对象外项目 | 理由 |
|---|---|---|
| OUT-01 | 系统状态监控（CPU / 内存 / 磁盘 / 进程） | 与 macOS 活动监视器功能重复 |
| OUT-02 | 任意命令输入执行 | 风险与收益不成比例，永久不做 |
| OUT-03 | 多机集中管理、远程访问 | 采用单机自治方针，永久不做 |
| OUT-04 | 用户账号与权限体系 | 仅本人使用，无必要 |
| OUT-05 | 定时任务、后台自动刷新 | 采用打开页面时取得的方针 |
| OUT-06 | Docker 容器管理 | 延至第二版，通过适配器接口接入 |
| OUT-07 | 端口占用查看与进程终止 | 延至第二版，通过适配器接口接入 |
| OUT-08 | sudo 提权操作 | 安全方针，永久不做 |
| OUT-09 | nvm / pyenv 版本管理 | 本机未安装。将来安装后通过追加适配器接入，不需变更既存要件 |
| OUT-10 | pip 用户级包 | 本机恒为 0 件（v3.2 起）。实装保留于 git 历史 |
| OUT-11 | uv 安装的命令行工具（`uv tool`） | `uv tool list` 无机器可读格式，且本机一个工具都没装，解析器无法实机验证。待真有工具时再接入 |

## 3. 功能要件

### 3.1 生态探测

| ID | 型 | 要件 |
|---|---|---|
| FR-01 | 事件驱动 | 当系统接收到生态清单取得请求时，系统应当对全部已注册的适配器执行探测处理。 |
| FR-02 | 异常处理 | 如果某适配器的探测处理返回不可用，则系统应当将该生态从生态清单中排除，且不生成错误通知。 |
| FR-03 | 异常处理 | 如果某适配器的探测处理抛出异常或超时，则系统应当将该生态视为不可用，且不影响其他适配器的探测。 |

> FR-02 的理由：使用者的多台机器环境本就不一致，「未安装」是常态而非异常状态。

### 3.2 条目清单显示

| ID | 型 | 要件 |
|---|---|---|
| FR-04 | 普遍性 | 系统应当按生态分卡片显示条目清单。 |
| FR-05 | 普遍性 | 系统应当为条目清单中的每个条目显示名称、当前版本、最新版本与状态。 |
| FR-06 | 普遍性 | 系统应当将条目状态表示为 `ok`、`outdated`、`unknown` 三者之一。 |
| FR-07 | 异常处理 | 如果无法取得某条目的最新版本，则系统应当将该条目的状态置为 `unknown`，且最新版本显示为「未知」。 |
| FR-08 | 可选特性 | 若生态具备「当前生效版本」的概念，系统应当在对应条目上标示其为当前生效。 |
| FR-09 | 事件驱动 | 当页面加载完成时，系统应当对全部可用生态并发发起条目清单取得请求。 |
| FR-10 | 状态驱动 | 在某生态的条目清单取得处理进行期间，系统应当在该生态的卡片内显示取得中状态，并保持其他卡片的显示与操作不受影响。 |
| FR-11 | 状态驱动 | 在某生态的条目清单取得处理进行期间，若该卡片已持有先前取得的内容，系统应当继续显示该内容并标示其为取得中。 |
| FR-12 | 事件驱动 | 当使用者点击某卡片的刷新按钮时，系统应当仅重新取得该生态的条目清单。 |

> FR-09、FR-10 的理由：Homebrew 相关命令需数秒至数十秒且依赖网络，不得因此阻塞其他生态的显示。

> FR-08 的适用范围：SC-01（Homebrew）与 SC-02（npm）不具备该概念，`active` 恒为 `null`。SC-03（uv 管理的 Python）自 v3.2 起成为首个适用对象 —— uv 会为某个 Python 在 `~/.local/bin` 下建立符号链接，该版本即为当前生效。

> FR-11 的理由：取得期间将已显示的内容清空会造成画面闪烁，且使用者在等待期间失去可读信息。本要件与 FR-22 不冲突 —— FR-22 禁止的是持久化至磁盘，而非内存中的保持。

### 3.3 操作执行

| ID | 型 | 要件 |
|---|---|---|
| FR-13 | 普遍性 | 系统应当依据条目的 `actions` 字段动态渲染该条目可用的操作按钮。 |
| FR-14 | 事件驱动 | 当使用者请求执行非破坏性操作时，系统应当直接执行该操作。 |
| FR-15 | 事件驱动 | 当使用者请求执行破坏性操作时，系统应当显示包含对象名称与操作种类的确认提示。 |
| FR-16 | 事件驱动 | 当使用者在确认提示中选择执行时，系统应当执行该操作。 |
| FR-17 | 异常处理 | 如果使用者在确认提示中选择取消，则系统应当中止该操作，且不向服务端发送请求。 |
| FR-18 | 状态驱动 | 在某操作执行期间，系统应当在对应卡片显示执行中状态，并禁用该卡片内的全部操作按钮。 |
| FR-19 | 异常处理 | 如果某生态已有操作正在执行，则系统应当拒绝该生态内的新操作请求。 |
| FR-20 | 事件驱动 | 当操作正常结束时，系统应当自动重新取得该生态的条目清单。 |
| FR-21 | 异常处理 | 如果操作以失败结束，则系统应当显示该命令的标准输出与标准错误输出，且不应当代之以无具体内容的失败提示。 |

> FR-13 的理由：并非所有生态都支持全部操作。界面不应当假定操作集合固定。

> FR-19 的理由：同一包管理器的并行写操作会导致锁竞争与状态不一致。限制粒度为「生态内」，不同生态之间允许并行。

> FR-21 的理由：「操作失败」一类无信息量的提示无法支撑排查，必须暴露原始输出。输出量的上限依 NFR-09。

### 3.4 条目的辅助信息

| ID | 型 | 要件 |
|---|---|---|
| FR-26 | 普遍性 | 系统应当为每个生态标示其管理对象所在的位置。 |
| FR-24 | 可选特性 | 若能取得条目的用途说明，系统应当显示中文简介；词典中无对应条目时，应当回落至包管理器给出的原文。 |
| FR-25 | 可选特性 | 若生态区分「主动安装」与「作为依赖被拖入」，系统应当在条目上标示其区别。 |

> FR-26 的理由：三个生态分别管理 `/usr/local`（Homebrew）、`~/.local`（npm）与 `~/.local/share/uv`（uv），而 `/usr/bin` 等 Apple 管理的目录不在任何一方的范围内。使用者需要知道面板管的是哪一块、哪些不管。位置须动态取得（NFR-12），不得硬编码。

> FR-25 的理由：实机调查确认，本机的 Homebrew 包中仅 4 个为主动安装，其余 35 个是依赖。使用者面对 `libngtcp2` 这类名称时，真正需要的判断不是「它是什么」而是「能不能卸」—— 单独卸载依赖会破坏依赖它的包。

> FR-24 的实装：`brew info --json` 与 `npm ls --long` 均提供英文的用途说明，包管理器不提供中文。故以词典覆盖已知条目，未收录者显示原文，不留空白。pip 的 `list` 不提供说明，逐包查询过慢，本版不做。

### 3.5 数据取得方针

| ID | 型 | 要件 |
|---|---|---|
| FR-22 | 普遍性 | 系统不应当将条目清单的取得结果持久化至磁盘。 |
| FR-23 | 事件驱动 | 当服务进程结束时，系统应当丢弃全部已取得的数据。 |

> 本节与 SEC-09 的关系：SEC-09 所需的条目 ID 集合保持于服务端内存，不属于持久化，不违反 FR-22。服务重启后该集合为空，其行为依 SEC-09 规定。

## 4. 非功能要件

### 4.1 要件

| ID | 型 | 要件 |
|---|---|---|
| NFR-01 | 普遍性 | 系统应当在 macOS 与 Node.js 22 以上的环境中运行。 |
| NFR-02 | 普遍性 | 系统应当仅使用 Node.js 标准库实现，不应当引入任何第三方运行时依赖。 |
| NFR-03 | 事件驱动 | 当使用者在新机器上克隆本仓库后，系统应当无需执行依赖安装即可启动。 |
| NFR-04 | 普遍性 | 系统应当可通过 `npm start` 启动。 |
| NFR-05 | 普遍性 | 系统应当从 `.env` 读取第 4.2 节所定义的配置项。 |
| NFR-06 | 异常处理 | 如果 `.env` 不存在，或某配置项未定义，则系统应当采用第 4.2 节的默认值启动，且不生成错误。 |
| NFR-07 | 异常处理 | 如果条目清单取得的子进程执行时间超过 `LIST_TIMEOUT_MS`，则系统应当终止该子进程所属的进程组并返回超时错误。 |
| NFR-08 | 异常处理 | 如果操作执行的子进程执行时间超过 `ACTION_TIMEOUT_MS`，则系统应当终止该子进程所属的进程组并返回超时错误。 |
| NFR-09 | 异常处理 | 如果子进程的标准输出或标准错误输出超过对应的输出上限，则系统应当截断该路输出、保留首尾两端，并在结果中标示已截断。 |
| NFR-10 | 普遍性 | 系统应当将生态固有的知识完全封装于适配器模块内，路由层与前端不应当包含任何具体生态的名称。 |
| NFR-11 | 事件驱动 | 当追加新生态时，系统应当仅通过新增适配器文件与注册来支持该生态，不应当要求修改路由层与前端。 |
| NFR-12 | 普遍性 | 系统不应当硬编码任何包管理器的安装路径，应当通过该工具自身的查询手段动态取得。 |
| NFR-13 | 异常处理 | 如果服务端发生未捕获的异常，则系统应当返回错误响应并维持服务进程继续运行。 |
| NFR-14 | 异常处理 | 如果 `PORT` 所指定的端口已被占用，则系统应当以包含变更方法的错误信息终止启动。 |

> NFR-02 的理由：零依赖使换机成本降为零，同时排除供应链风险。本面板界面复杂度低，原生实现足够。

> NFR-07、NFR-08 分离的理由：条目清单取得为只读查询，数十秒内必然结束；而 `brew upgrade` 等操作可能触发源码编译，需要数分钟至十数分钟。以单一超时值同时覆盖两者，会导致要么查询卡顿过久、要么操作被中途杀死。

> NFR-07、NFR-08 以进程组为终止单位的理由：实装阶段确认，仅终止直接子进程时，其派生的孙进程会继续持有标准输出管道，导致进程结束事件永不到达、请求永久挂起。`brew upgrade` 触发源码编译正是此情形。

> NFR-09 的截断单位为「每一路输出」而非两路合计。标准错误输出通常是排查的关键，不应被大量标准输出挤占额度。

> 清单与操作的输出上限分离的理由：操作输出的上限是显示用的，截断成首尾两段仍可读；而清单取得的输出是待解析的 JSON，一旦截断即完全不可用。实测 43 件 Homebrew 包的输出为 148 KB，约 3.5 KB/件，以 1 MiB 为上限约在 300 件触顶。二者性质不同，不应共用一个预算。

> NFR-12 的理由：实机调查确认本机为 Intel 架构，Homebrew 前缀为 `/usr/local`。Apple Silicon 机器的前缀为 `/opt/homebrew`。硬编码路径将导致代码无法在使用者的其他机器上运行。

### 4.2 配置项与默认值

| 配置项 | 默认值 | 用途 |
|---|---|---|
| `PORT` | `7788` | HTTP 服务端口 |
| `LIST_TIMEOUT_MS` | `60000` | 条目清单取得的子进程超时（60 秒） |
| `ACTION_TIMEOUT_MS` | `600000` | 操作执行的子进程超时（10 分钟） |
| `LIST_MAX_OUTPUT_BYTES` | `16777216` | 条目清单取得的输出上限（16 MiB） |
| `ACTION_MAX_OUTPUT_BYTES` | `1048576` | 操作执行的输出上限（1 MiB） |
| `AUTO_OPEN_BROWSER` | `true` | 启动时是否自动打开浏览器 |

> 配置值的校验：数值项须为取值域内的整数，布尔项须为可识别的真假值。无效值将打印警告并退回默认值（实装阶段追加，NFR-06 的延伸）。

> 请求体的上限为 64 KiB，超过时以 `413` 拒绝（7.6 节）。该值不可配置 —— 合法请求体仅含条目 ID 与确认标记，远小于此。

> 端口采用固定值而非随机值的判断：安全边界由 SEC-01（仅绑定 `127.0.0.1`）与 SEC-04（令牌必需）构成。在此前提下随机端口仅增加「地址不可预测」的不便，不提供实质的安全增益。

## 5. 安全要件

本面板可执行卸载等破坏性操作。以下要件全部为必须项，不接受以「仅本人使用」为由的妥协。

| ID | 型 | 要件 |
|---|---|---|
| SEC-01 | 普遍性 | 系统应当仅将 HTTP 服务绑定至 `127.0.0.1`，不应当绑定至 `0.0.0.0` 或任何外部可达地址。 |
| SEC-02 | 事件驱动 | 当服务启动时，系统应当生成一个密码学安全的随机访问令牌。 |
| SEC-03 | 事件驱动 | 当服务启动时，系统应当向标准输出打印包含访问令牌的访问 URL。 |
| SEC-04 | 普遍性 | 系统应当对 `/api/` 下的全部端点要求有效的访问令牌。 |
| SEC-05 | 普遍性 | 系统不应当对静态资源端点要求访问令牌。 |
| SEC-06 | 异常处理 | 如果 `/api/` 请求未携带访问令牌，或所携带的令牌与本次启动生成的令牌不一致，则系统应当以 `401` 拒绝该请求。 |
| SEC-07 | 异常处理 | 如果 POST 请求未携带 `Origin` 头，或其值不在本服务的来源白名单中，则系统应当以 `403` 拒绝该请求。 |
| SEC-08 | 异常处理 | 如果请求指定的操作种类未在对应适配器中声明，则系统应当以 `400` 拒绝该请求。 |
| SEC-09 | 异常处理 | 如果请求指定的条目 ID 不存在于该生态最近一次条目清单取得的结果中，则系统应当以 `409` 拒绝该请求，并提示使用者先刷新该生态的条目清单。 |
| SEC-10 | 异常处理 | 如果破坏性操作的请求体的 `confirm` 字段不为 `true`，则系统应当以 `400` 拒绝该请求。 |
| SEC-11 | 普遍性 | 系统应当将命令与参数以数组形式传递给子进程，不应当经由 shell 拼接字符串。 |
| SEC-12 | 普遍性 | 系统不应当使用 `sudo`，也不应当提供任何提权入口。 |
| SEC-13 | 事件驱动 | 当前端从 URL 查询参数取得访问令牌后，系统应当将该查询参数从浏览器地址栏中移除。 |

> SEC-01 的理由：服务若绑定至外部可达地址，同一局域网内的第三方即可访问具备破坏性操作能力的面板。

> SEC-05 的理由：静态资源仅为不含任何数据的空壳页面。若对其要求令牌，则浏览器在取得令牌之前无法载入页面，形成循环依赖。数据一律经 `/api/` 提供，令牌防线设于该层即可。

> SEC-07 的来源白名单为 `http://127.0.0.1:<PORT>` 与 `http://localhost:<PORT>` 两项。同时允许二者不削弱防护，理由是：`Origin` 由浏览器按**发起文档的源**填写，而源由 URL 的 scheme / host / port 三者决定。跨站攻击者的文档源为其自身域名，无法取得一个源为 `http://localhost:<PORT>` 的文档；DNS rebinding 也不行 —— 即使 `evil.com` 重绑至回环地址，文档的源仍是 `http://evil.com`。攻击者若在本机自跑服务，其端口必然不同，而端口精确参与比较。
>
> **本项防护成立的前提是比较为精确字符串相等。** 任何退化为子串匹配或前缀匹配的实装都会直接推翻上述论证（例如 `http://localhost` 不带端口将被放行）。故 `checkOrigin` 须校验白名单为数组。

> SEC-07 的理由：浏览器的同源策略无法阻止跨站发出的写请求。使用者浏览其他网页时，恶意页面可向本地服务发送请求。浏览器对 `fetch` 发起的 POST 必定附加 `Origin` 头，因此「缺失」即为异常，应与「不一致」同样拒绝。

> SEC-09 的实现前提：服务端在内存中保持各生态最近一次条目清单的条目 ID 集合，仅用于本项校验。服务重启后该集合为空，此时的操作请求将被拒绝，使用者需先刷新条目清单。

> SEC-13 的理由：令牌若残留于地址栏，将被记入浏览器历史，并可能随复制粘贴外泄。前端读取后应立即以 `history.replaceState` 清除。

> SEC-08、SEC-09、SEC-11 构成命令注入的三重防线：操作种类白名单、操作对象白名单、无字符串拼接。

## 6. 架构设计

### 6.1 方针

采用适配器模式。各生态实现统一接口，路由层与前端仅依赖该统一接口，不持有任何具体生态知识（NFR-10）。

采用理由：第二版确定要追加 Docker 与端口管理（OUT-06、OUT-07），将来亦可能接入 nvm / pyenv（OUT-09）。适配器的抽象成本为一次性支出，而为各生态分别实现路由与界面的重复成本会在每次扩展时重复发生。此外探测处理（FR-01）天然覆盖「本机未安装该生态」的情形，契合多机环境不一致的实际状况。

## 7. 接口定义

### 7.1 适配器接口

```js
{
  id: 'homebrew',              // 唯一标识。URL 路径中使用
  label: 'Homebrew',           // 卡片标题的显示名
  detect(): Promise<boolean>,  // 本机是否可用（FR-01～FR-03）
  location(): Promise<string|null>,   // 管理对象所在的位置。须动态取得（FR-26、NFR-12）
  list():   Promise<Item[]>,   // 条目清单（FR-05～FR-08）
  actions: {
    [actionKey]: {
      label: '更新',                        // 按钮的显示名
      destructive: false,                   // 是否需要二次确认（FR-15）
      run(item: Item): Promise<ActionResult>
    }
  }
}
```

> `run(item)` 只得依赖 `item` 的 `id` 与 `name`。传入的条目来自最近一次 `list()` 的快照，`current` 与 `latest` 可能已过时，以其拼装命令会指向错误的对象。

### 7.2 条目 Item

```js
{
  id: 'ripgrep',            // 生态内唯一。SEC-09 的白名单比对对象
  name: 'ripgrep',          // 显示名
  current: '14.1.0',        // 当前版本
  latest: '14.1.1',         // 最新版本。无法取得时为 null（FR-07）
  status: 'outdated',       // 'ok' | 'outdated' | 'unknown'（FR-06）
  active: null,             // true=当前生效 / false=非生效 / null=该生态无此概念（FR-08）
  description: '加密与 TLS 工具包',   // 中文简介。取不到时为 null（FR-24）
  requested: false,         // true=主动安装 / false=被依赖拖入 / null=该生态无此概念（FR-25）
  actions: ['update', 'uninstall']   // 该条目可用的操作键（FR-13）
}
```

### 7.3 操作请求 ActionRequest

`POST /api/adapters/:id/actions/:action` 的请求体。

```js
{
  itemId: 'ripgrep',   // 操作对象。SEC-09 的校验对象
  confirm: true        // 破坏性操作时必须为 true（SEC-10）
}
```

### 7.4 操作结果 ActionResult

```js
{
  ok: true,            // 操作是否成功
  exitCode: 0,         // 子进程的退出码。被信号终止时为 null
  signal: null,        // 终止该进程的信号名。正常退出时为 null（FR-21）
  stdout: '...',       // 标准输出（FR-21）
  stderr: '...',       // 标准错误输出（FR-21）
  truncated: false     // 输出是否被截断（NFR-09）
}
```

> `signal` 字段于实装阶段追加。`exitCode` 在子进程被信号终止时为 `null`，仅此无法判别终止原因，不足以支撑 FR-21 所要求的排查。

### 7.5 API 端点

| 方法 | 路径 | 令牌 | 说明 | 关联要件 |
|---|---|---|---|---|
| GET | `/` | 否 | `web/index.html` | SEC-05 |
| GET | `/app.js`、`/style.css` | 否 | 静态资源 | SEC-05 |
| GET | `/api/adapters` | 是 | 本机可用的生态清单（含 `label`、`location`、操作元数据） | FR-01～FR-03、FR-26 |
| GET | `/api/adapters/:id/items` | 是 | 指定生态的条目清单 | FR-05～FR-08 |
| POST | `/api/adapters/:id/actions/:action` | 是 | 对指定条目执行操作 | FR-14～FR-21 |

### 7.6 错误响应

全部错误响应共用以下结构。

```js
{
  error: {
    code: 'STALE_ITEM',                       // 机器可判别的错误种别
    message: '该条目已不在最新的清单中，请先刷新。',   // 向使用者提示的文本
    detail: '...'                             // 原始输出等补充信息。无则为 null
  }
}
```

| HTTP | `code` | 发生条件 | 要件 |
|---|---|---|---|
| 400 | `BAD_BODY` | 请求体无法解析 | — |
| 400 | `UNKNOWN_ACTION` | 操作种类未声明 | SEC-08 |
| 400 | `CONFIRM_REQUIRED` | 破坏性操作缺少确认标记 | SEC-10 |
| 401 | `INVALID_TOKEN` | 令牌缺失或不一致 | SEC-06 |
| 403 | `BAD_ORIGIN` | `Origin` 缺失或不一致 | SEC-07 |
| 409 | `STALE_ITEM` | 条目 ID 不在最近一次清单中 | SEC-09 |
| 409 | `BUSY` | 该生态已有操作执行中 | FR-19 |
| 404 | `UNKNOWN_ADAPTER` | 路径指定的生态不存在 | — |
| 404 | `NOT_FOUND` | 未知的端点 | — |
| 413 | `PAYLOAD_TOO_LARGE` | 请求体超过上限 | — |
| 500 | `INTERNAL` | 本服务自身的缺陷 | NFR-13 |
| 502 | `ADAPTER_FAILED` | 适配器的下游命令失败、工具不可执行或输出无法解析 | — |
| 504 | `TIMEOUT` | 子进程超时 | NFR-07、NFR-08 |

> 502 与 500 的分界：断网、工具未安装、输出无法解析等属下游的运行时状况，重试或修正环境可能有效；500 保留给本服务自身的缺陷。二者在界面上不应难以分辨。

## 8. 错误处理方针

基本原则：**降级、不崩溃、不静默**。

具体行为已在各章要件中规定，此处为汇总索引，不重复定义。

| 状况 | 处理 | 要件 |
|---|---|---|
| 探测返回不可用 | 该生态从生态清单排除，不视为错误 | FR-02 |
| 探测抛出异常或超时 | 同上，且不影响其他适配器 | FR-03 |
| 条目清单取得失败 | 仅该卡片显示错误与重试手段，不影响其他卡片 | ERR-01 |
| 最新版本无法取得 | 状态置为 `unknown` | FR-07 |
| 子进程超时 | 终止进程组并返回 `TIMEOUT` | NFR-07、NFR-08 |
| 输出过大 | 截断并保留首尾，标示已截断 | NFR-09 |
| 操作失败 | 显示标准输出与标准错误输出 | FR-21 |
| 服务端未捕获异常 | 返回 `INTERNAL` 并维持进程 | NFR-13 |
| 端口被占用 | 以包含变更方法的信息终止启动 | NFR-14 |

本章新增要件仅以下一件：

| ID | 型 | 要件 |
|---|---|---|
| ERR-01 | 异常处理 | 如果某生态的条目清单取得失败，则系统应当在该生态的卡片内显示错误信息、标准错误输出的末尾部分与重试手段，并保持其他卡片的显示不受影响。 |

## 9. 测试方针

### 9.1 可测性设计

各适配器须将「执行命令」与「解析输出」分离，解析部分实现为纯函数，使测试不依赖本机实际安装状态。

```js
function parseBrewList(stdout) { ... }        // 纯函数，单元测试对象
async function list() { return parseBrewList(await exec(...)); }
```

### 9.2 自动测试对象

| 对象 | 内容 | 验证要件 |
|---|---|---|
| 解析函数 | 以实际命令输出样本为输入，覆盖正常、空清单、格式异常三种情形 | FR-05～FR-08 |
| `security.js` | 令牌校验、`Origin` 校验（含缺失）、操作白名单、条目白名单、确认标记校验 | SEC-04、SEC-06～SEC-10 |
| `exec.js` | 超时时子进程与孙进程确实被终止、输出截断与 `truncated` 标示、参数以数组传递 | NFR-07～NFR-09、SEC-11 |
