| 项目 | 内容 |
|---|---|
| 审查对象 | `docs/specs/2026-09-20-os-tool-manager-requirements.md`（版本 2.0，制定日 2026-09-20，状态「已确认」） |

| 审查方法 | 全 367 行逐行通读；全部 49 个 ID（FR/NFR/SEC/ERR/SC/OUT）的定义处与引用处机械提取比对；件数实际计数 |
| 发现件数 | 合计 32 件（高 6 / 中 17 / 低 9） |

### 结论概要

文档的骨架质量高：ID 编号完全连续无重复，附录 A 的件数统计经实际计数确认**完全正确**，全部被引用的 ID 均真实存在，章节间的方针（零依赖・单机自治・适配器模式）贯彻一致。

但存在**可直接阻碍进入仕様书阶段的 6 件高严重度问题**，集中在两处：
1. **第 4 章与第 5 章的正面矛盾**（NFR-05 允许端口固定 vs SEC-02 要求随机端口；NFR-03 的「克隆即可启动」vs `.env` 为版本控制对象外）。
2. **第 5 章要求的安全机制在第 7 章接口定义中没有落点**（访问令牌如何送达浏览器未定义；POST 请求体结构完全缺失，导致 SEC-06 的条目 ID 与 SEC-08 的确认标记无处承载）。

此外 FR-19（不使用既存取得结果）与 FR-09/FR-10（刷新期间的卡片显示）之间存在实装级别的矛盾，必须在设计前消解。

建议：**不宜以当前状态直接进入仕様书**。先处理 6 件高严重度与其中关联的中严重度项（约需一次修订），再着手详细设计。

## 高严重度（6 件）

### ISS-01 ｜高｜内部矛盾｜4 章 NFR-05 × 5 章 SEC-02

**位置**：NFR-05（第 4 章）、SEC-02（第 5 章）

**问题描述**

NFR-05：
> 系统应当从 `.env` 读取机器固有配置（**超时时长、端口固定与否**）。

SEC-02：
> 当服务启动时，系统应当**生成随机端口**与随机访问令牌。

NFR-05 明确将「端口固定与否」作为可配置项，即承认存在「端口被固定」的形态；而 SEC-02 是无条件的事件驱动要件，要求每次启动都生成随机端口。两者对同一属性给出互斥的规定，实装者无法判断应遵循哪一条。并且第 5 章开头声明「以下要件全部为必须项，不接受以『仅本人使用』为由的妥协」，进一步强化了冲突。

另外，随机端口的安全价值本身有限（SEC-01 的 `127.0.0.1` 绑定与 SEC-03 的令牌校验才是实质防线），而固定端口对「加书签」的实用价值明确。建议以 SEC-02 让步的方向消解。

**修改建议**

将 SEC-02 拆分为两条，并明示端口的可配置性：

| ID | 型 | 要件 |
|---|---|---|
| SEC-02 | 事件驱动 | 当服务启动时，系统应当生成长度 32 字节以上的随机访问令牌，且该令牌不应当在进程间持久化。 |
| SEC-02b | 复合 | 当服务启动时，若 `.env` 未指定端口，系统应当绑定至由 OS 分配的空闲端口；若 `.env` 指定了端口，系统应当绑定至该端口。 |

并在 SEC-02 下追加理由注释：

> SEC-02 的理由：端口的随机化不构成安全边界（防线为 SEC-01 的绑定限制与 SEC-03 的令牌校验），因此允许依 NFR-05 固定端口以便加书签。令牌的随机性与每次启动的更新则是必须项。

### ISS-02 ｜高｜完整性｜5 章 SEC-02・SEC-03 × 7 章

**位置**：SEC-02、SEC-03（第 5 章）、7.3 节 API 端点表

**问题描述**

SEC-02 规定服务启动时生成随机访问令牌，SEC-03 规定：
> 如果请求未携带有效的访问令牌，则系统应当拒绝该请求。

但文档中**完全没有规定令牌如何送达浏览器**，也没有规定使用者如何得知服务的 URL（在 SEC-02 的随机端口前提下，URL 本身也是未知的）。同时存在「先有鸡还是先有蛋」的问题：前端 `web/index.html` 本身也是通过 HTTP 取得的，若 SEC-03 对全部请求生效，则页面本身也无法加载。

7.3 节的端点表只列出 3 个 `/api/*` 端点，**没有任何静态资源交付端点**，因此 `web/index.html`、`app.js`、`style.css`（6.2 节明确存在）通过什么路径交付、是否受 SEC-03 约束，均无规定。这是无法据以实装的缺口。

**修改建议**

在第 5 章追加两条要件，并在 7.3 节追加端点行。

| ID | 型 | 要件 |
|---|---|---|
| SEC-10 | 事件驱动 | 当服务启动完成时，系统应当将含有访问令牌的完整 URL（形如 `http://127.0.0.1:<port>/?token=<token>`）输出至标准输出。 |
| SEC-11 | 复合 | 当请求的路径为静态资源（`/`、`/app.js`、`/style.css`）时，系统应当不施加 SEC-03 的令牌校验；当请求的路径以 `/api/` 开头时，系统应当施加 SEC-03 的令牌校验。 |

7.3 节追加：

| 方法 | 路径 | 说明 | 关联要件 |
|---|---|---|---|
| GET | `/`、`/app.js`、`/style.css` | 交付前端静态资源（不需令牌） | SEC-11 |

并追加注释：

> SEC-11 的理由：静态资源不含任何本机信息，且页面自身需在持有令牌前被载入。令牌由 URL 查询参数传入后，前端将其保存于内存，并附加于其后的全部 `/api/` 请求（`X-Token` 头）。静态资源的破坏性为零，故无令牌校验的必要。

同时需在第 5 章明示令牌的传递手段（`X-Token` 请求头）——否则 SEC-03 的「携带」一词仍属未定义。

### ISS-03 ｜高｜歧义／安全｜5 章 SEC-04

**位置**：SEC-04（第 5 章）

**问题描述**

> SEC-04：如果 POST 请求的 `Origin` 头与本服务的地址**不一致**，则系统应当拒绝该请求。

「不一致」未涵盖「`Origin` 头**不存在**」的情形。严格按字面实装（`if (origin !== expected) reject`）恰好能拒绝缺失情形，但按「比较两者是否一致」的自然语义实装（`if (origin && origin !== expected) reject`）则会放行无 `Origin` 头的请求。这是一条可被两种方式理解的要件，且两种理解的安全后果截然不同——而 `curl`、部分非浏览器客户端、以及某些 `<form>` 提交确实不发送 `Origin`。

SEC-04 的理由注释指出此项是防范跨站写请求的「必要防线」，越是如此，越不能留下这个歧义。

**修改建议**

改写为：

| ID | 型 | 要件 |
|---|---|---|
| SEC-04 | 异常处理 | 如果 POST 请求未携带 `Origin` 头，或其 `Origin` 头的值与本服务的源（`http://127.0.0.1:<port>`）不完全一致，则系统应当拒绝该请求。 |

### ISS-04 ｜高｜完整性｜5 章 SEC-06・SEC-08 × 7 章

**位置**：SEC-06、SEC-08（第 5 章）、7.1 / 7.2 / 7.3 节

**问题描述**

SEC-06 要求校验「请求指定的**条目 ID**」，SEC-08 要求校验「请求体是否携带**确认标记**」。但第 7 章的接口定义中：

- 7.1 适配器接口 —— 只定义了 `detect()` / `list()` / `actions.run(item)`；
- 7.2 条目结构 Item —— 是**响应**侧的结构；
- 7.3 API 端点 —— `POST /api/adapters/:id/actions/:action` 一行，**无请求体定义**。

即，SEC-06 与 SEC-08 所校验的两个输入项，在接口定义中没有任何落点。实装者必须自行发明请求体格式，这正是要件定义书应当消除的不确定性。同理，7.1 的 `run(item)` 接收的 `item` 从何而来（客户端送来的完整对象？还是服务端以 ID 从白名单集合取回的对象？）也未定义——若采用前者，SEC-06 的白名单校验将形同虚设。

**修改建议**

在 7.2 节之后追加 7.2b 节：

````
### 7.2b 操作请求体 ActionRequest

```js
{
  itemId: 'ripgrep',   // 操作对象的条目 ID（SEC-06 的校验对象）
  confirm: true        // 破坏性操作时必须为 true（SEC-08 的校验对象）
}
```

服务端不接受客户端送来的 Item 对象本体。`run()` 接收的 `item` 一律由服务端以
`itemId` 从 SEC-06 的白名单集合中取回，以防客户端伪造条目内容。
````

并在 7.3 节的 POST 行「关联要件」列补入 `SEC-05、SEC-06、SEC-08`。

### ISS-05 ｜高｜内部矛盾｜4 章 NFR-03・NFR-05 × 6.2 节

**位置**：NFR-03、NFR-05（第 4 章）、6.2 节目录构成

**问题描述**

NFR-03：
> 当使用者在新机器上克隆本仓库后，系统应当**无需执行依赖安装即可启动**。

NFR-05：
> 系统应当从 `.env` 读取机器固有配置。

6.2 节：
> `└── .env                   机器固有配置（**版本控制对象外**）`

三者组合的结论是：克隆后的新机器上 `.env` **必然不存在**。而文档从未规定 `.env` 不存在时的行为。若实装者按 NFR-05 的字面（「应当从 `.env` 读取」）实装为必需文件，则启动失败，直接违反 NFR-03；若实装为可选，则 NFR-05 的「应当」含义被架空。第 1.4 节「同一份代码通过 Git 分发到本人的多台 Mac」正是此问题的高频场景。

**修改建议**

将 NFR-05 改写为两条，明示缺省行为与默认值：

| ID | 型 | 要件 |
|---|---|---|
| NFR-05 | 可选特性 | 若 `.env` 文件存在，系统应当从中读取机器固有配置（子进程超时时长、输出上限、端口）。 |
| NFR-05b | 异常处理 | 如果 `.env` 文件不存在，或其中某配置项未定义，则系统应当采用该项的默认值启动，且不应当中止启动。 |

并在第 4 章追加默认值表（同时解决 ISS-09）：

| 配置项 | 环境变量名 | 默认值 |
|---|---|---|
| 子进程超时时长 | `EXEC_TIMEOUT_MS` | 60000 |
| 子进程输出上限 | `EXEC_MAX_OUTPUT_BYTES` | 262144 |
| 端口 | `PORT` | 未指定时由 OS 分配 |

另需在仓库中追加 `.env.example`，并在 6.2 节目录构成中列出。

### ISS-06 ｜高｜内部矛盾｜3.4 节 FR-19 × 3.2 节 FR-09・FR-10

**位置**：FR-19（3.4 节）、FR-09・FR-10（3.2 节）

**问题描述**

FR-19：
> 系统**不应当将既存的取得结果用于界面显示**。

FR-09：
> 在某生态的一览取得处理进行期间，系统应当**仅在该生态的卡片内显示加载状态**，并保持其他卡片的显示与操作不受影响。

FR-10 触发的是「重新取得」，即卡片中已有上一次的一览。此时按 FR-09，卡片内显示加载状态——但**卡片内既有的条目行是否继续显示**？

- 若继续显示 → 正在用「既存的取得结果」进行界面显示，违反 FR-19。
- 若清空 → 每次刷新都会出现闪烁与高度塌陷，且 FR-09 的「其他卡片不受影响」这一措辞暗示的正是「受影响的卡片保留可视上下文」。

FR-19 的意图（不做跨会话的缓存持久化、不以陈旧数据冒充实时数据）是正确的，但当前措辞覆盖范围过宽，把「刷新期间的过渡显示」也一并禁止了。FR-19 的补充注释只把 SEC-06 的 ID 集合列为「唯一例外」，反而堵死了上述解释空间。

**修改建议**

将 FR-19 的适用对象限定为「跨越取得处理的陈旧数据」，并明确刷新期间的显示规则：

| ID | 型 | 要件 |
|---|---|---|
| FR-19 | 普遍性 | 系统不应当将上一次会话或上一次启动时的取得结果持久化，也不应当在未执行实际命令的情况下向使用者呈现一览内容。 |
| FR-19b | 状态驱动 | 在某生态的一览重新取得期间，系统应当保持该卡片中上一次取得的条目继续显示，并同时以视觉方式标示该内容为更新中。 |

并将 FR-19 的补充注释改写为：

> FR-19 的补充：SEC-06 所需的条目 ID 集合保留于服务端内存中，仅用于安全校验，不用于显示，且随进程结束而消失，因此不构成持久化。FR-19b 所述的更新中显示不属于「未执行实际命令的呈现」——该期间实际命令正在执行中。

## 中严重度（17 件）

### ISS-07 ｜中｜EARS 合规性｜3.3 节 FR-14

**位置**：FR-14（3.3 节）

**问题描述**

> | FR-14 | **复合** | 当使用者请求执行破坏性操作时，系统应当要求二次确认；**仅在取得确认后，系统应当执行该操作。** |

第 0 章对「复合」的定义是「上述句型的**组合**……需同时限定状态与事件」。而 FR-14 的实态是**两条独立的事件驱动要件用分号连接**（触发1＝请求破坏性操作 → 响应1＝要求确认；触发2＝取得确认 → 响应2＝执行），并非状态与事件的复合。这既是型标注错误，也是「一条要件里塞了多个独立要求」的典型案例——两者的测试用例完全不同（前者验证确认对话框出现，后者验证取消时不执行）。

**修改建议**

拆分为两条事件驱动要件：

| ID | 型 | 要件 |
|---|---|---|
| FR-14 | 事件驱动 | 当使用者请求执行破坏性操作时，系统应当显示含操作名与对象名的确认提示，且在此时点不应当执行该操作。 |
| FR-14b | 事件驱动 | 当使用者在确认提示中选择执行时，系统应当执行该操作；当使用者选择取消时，系统应当放弃该操作且不发出任何请求。 |

后续引用处（7.3 节「FR-13～FR-17」）随之更新为「FR-13～FR-17（含 FR-14b）」，或将 FR-14b 改号以保持范围表记的连续性（推荐重编号为 FR-14 / FR-15，其后顺延）。

### ISS-08 ｜中｜歧义・内部矛盾｜8 章 ERR-01 × 3.3 节 FR-17 × 4 章 NFR-07

**位置**：ERR-01（第 8 章）、FR-17（3.3 节）、NFR-07（第 4 章）

**问题描述**

ERR-01：
> ……系统应当在该生态的卡片内显示错误信息、**标准错误输出的摘要**与重试手段……

「摘要」是全文**唯一**的模糊词（已机械检索确认），且与同文档的两条要件方针不一致：

- FR-17 对操作失败要求「显示该命令的**原始输出**，且不得代之以无具体内容的失败提示」；
- NFR-07 对过大输出规定的处理是「**截断**该输出并保留首尾部分」，而非「摘要」。

即，同一份 stderr，在「一览取得失败」时要「摘要」、在「操作失败」时要「原始输出」，两者的差异既无理由说明，「摘要」本身也不可验证（谁来生成摘要？按什么规则？）。第 8 章开头的原则「不静默」更支持保留原文。

**修改建议**

统一为「原始输出（依 NFR-07 截断）」：

| ID | 型 | 要件 |
|---|---|---|
| ERR-01 | 异常处理 | 如果某生态的一览取得失败，则系统应当在该生态的卡片内显示错误信息、该命令的标准错误输出原文（超过 NFR-07 的上限时依 NFR-07 截断）与重试按钮，并保持其他卡片的显示与操作不受影响。 |

（同时补入「与操作」，使之与 FR-09 的措辞一致——参见 ISS-19。）

### ISS-09 ｜中｜完整性｜4 章 NFR-07 × NFR-05

**位置**：NFR-07、NFR-05（第 4 章）

**问题描述**

> NFR-07：如果子进程的输出超过**配置的上限**，则系统应当截断该输出并保留首尾部分。

NFR-06 在同样的位置给出了默认值（「默认 60 秒」），而 NFR-07 的「配置的上限」**既无默认值，也未出现在 NFR-05 所列的 `.env` 配置项中**（NFR-05 只列「超时时长、端口固定与否」）。因此「配置的上限」指向一个文档中不存在的配置项，该要件不可验证：测试无从判定截断是否在正确的阈值发生。

另外「保留首尾部分」未规定首尾各保留多少，同属不可验证。

**修改建议**

改写为：

| ID | 型 | 要件 |
|---|---|---|
| NFR-07 | 异常处理 | 如果子进程的输出超过配置的上限（默认 256 KiB），则系统应当保留开头与末尾各半数的字节并舍弃中间部分，且应当在舍弃处插入表明已截断及舍弃字节数的标记行。 |

并依 ISS-05 的建议，在 NFR-05 的配置项中补入输出上限。

### ISS-10 ｜中｜交叉引用｜6.3 节・9.2 节 × SEC-07

**位置**：6.3 节 `security.js` 行、9.2 节 `security.js` 行

**问题描述**

6.3 节：
> | `security.js` | 安全校验 | 不得含业务判断 | **SEC-03～SEC-08** |

该范围包含 SEC-07：
> SEC-07：系统应当将命令与参数以数组形式传递给子进程，不应当经由 shell 拼接字符串。

### ISS-18 ｜中｜歧义｜「一览」一词的二义性

**位置**：FR-01、FR-02（3.1 节）、FR-04・FR-08～FR-10（3.2 节）、FR-16、ERR-01、SEC-06、7.3 节、第 11 章

**问题描述**

「一览」在文档中指代两个不同的对象：

- **生态的一览**（`GET /api/adapters` 的返回）：FR-01「当系统接收到**生态一览**取得请求时」、FR-02「将该生态从**一览**中排除」；
- **条目的一览**（`GET /api/adapters/:id/items` 的返回）：FR-08「并发发起**一览取得**请求」、FR-10「仅重新取得该生态的**一览**」、FR-16、ERR-01、SEC-06「该生态最近一次**一览取得**的结果」。

FR-02 的「从一览中排除」用的是第一义，而紧随其后的 FR-08「一览取得请求」用的是第二义，中间没有任何区分标记。第 11 章用语表**未收录「一览」**，读者只能靠上下文推断。SEC-06 的「最近一次一览取得的结果」若被误读为第一义，安全校验的实装会完全错位。

同样地，「卡片」（FR-04、FR-09、FR-15、ERR-01 中频繁出现，是前端的核心显示单位）与「操作种类」（SEC-05）也未收录于用语表。

**修改建议**

全文统一用词：第一义一律写作「**生态一览**」，第二义一律写作「**条目一览**」。据此需修改 FR-02、FR-08、FR-09、FR-10、FR-16、ERR-01、SEC-06、8 章汇总表、9.2 节。

并在第 11 章用语表追加：

| 用语 | 说明 |
|---|---|
| 生态一览 | 本机可用的生态的列表。`GET /api/adapters` 的返回内容 |
| 条目一览 | 某一生态内的条目的列表。`GET /api/adapters/:id/items` 的返回内容 |
| 卡片 | 前端中对应单一生态的显示单位。含该生态名、条目一览、刷新按钮与状态显示 |
| 操作种类 | 适配器的 `actions` 中声明的键（`update`、`uninstall` 等） |

### ISS-19 ｜中｜完整性｜并发操作的未规定

**位置**：FR-15（3.3 节）、FR-09（3.2 节）、ERR-01（第 8 章）

**问题描述**

FR-15：
> 在某操作执行期间，系统应当在对应卡片显示执行中状态，并**禁用该条目的全部操作按钮**。

禁用范围被明确限定为「该条目」，因此以下并发状况的行为**全部未规定**：

1. 某条目的卸载执行中，使用者点击**同一卡片内另一条目**的更新按钮 —— 允许吗？Homebrew 不支持并发 `brew` 操作（会因 lock 而失败）。
2. 某条目的操作执行中，使用者点击**该卡片的刷新按钮**（FR-10）—— 允许吗？若允许，刷新完成后条目被重绘，FR-15 的「执行中状态」将丢失。
3. 操作完成后 FR-16 触发自动重新取得，与使用者手动触发的 FR-10 重叠时，两个响应的到达顺序不定。

另外 FR-09 的措辞是「保持其他卡片的显示**与操作**不受影响」，而 ERR-01 只写「保持其他卡片的**显示**不受影响」，少了「与操作」——同类要件的措辞不一致（ISS-08 的建议中已一并修正）。

对本项目而言，1 是必须规定的（会产生实际的命令失败），2、3 是必须规定的（会产生可见的界面错乱）。

**修改建议**

将 FR-15 的禁用范围扩大至卡片单位，并追加一条：

| ID | 型 | 要件 |
|---|---|---|
| FR-15 | 状态驱动 | 在某生态的操作执行期间，系统应当在该卡片显示执行中状态，并禁用该卡片内的全部操作按钮与刷新按钮。 |
| FR-15b | 状态驱动 | 在某生态的操作执行期间，系统应当保持其他卡片的显示与操作不受影响。 |
| FR-20 | 异常处理 | 如果对同一生态的取得请求在前一次取得尚未完成时再次发起，则系统应当放弃先行请求的结果，仅采用最后一次请求的结果进行显示。 |

### ISS-20 ｜中｜内部矛盾｜4 章 NFR-06 的超时值 × 操作的实际所需时长

**位置**：NFR-06（第 4 章）、FR-08 的理由注释、第 10 章

**问题描述**

NFR-06：
> 如果子进程的执行时间超过配置的超时值（**默认 60 秒**），则系统应当终止该子进程并返回超时错误。

该要件对**全部子进程**一律适用，包括操作执行（`brew upgrade`、`brew uninstall`）。而 FR-08 的理由注释自认：
> Homebrew 相关命令需**数秒至数十秒**且依赖网络。

`brew upgrade` 单个包的实际耗时经常超过 60 秒（源码编译、大型 cask 下载可达数分钟）。按 NFR-06，这类操作会被系统主动终止——而 `brew` 被 SIGTERM 中断可能留下不完整的安装状态与残留的 lock。这与第 1.5 节的典型场景 2「批量确认哪些 Homebrew 包有更新，并选择性更新」直接冲突：该场景下的主力操作会频繁超时。

将默认值统一调高又会损害探测处理（`detect()`）——探测应在 1～2 秒内失败，否则页面加载会被拖慢，违背 FR-08 的意图。因此**单一超时值无法同时满足两侧**。

**修改建议**

按用途区分超时值：

| ID | 型 | 要件 |
|---|---|---|
| NFR-06 | 异常处理 | 如果子进程的执行时间超过其用途所对应的超时值，则系统应当终止该子进程并返回超时错误。用途别的默认值为：探测处理 5 秒、一览取得 60 秒、操作执行 600 秒。 |

并在 NFR-05 的配置项中提供三者各自的覆盖手段（`EXEC_TIMEOUT_DETECT_MS` / `_LIST_MS` / `_ACTION_MS`）。

### ISS-21 ｜中｜完整性・歧义｜4 章 NFR-01 的动作环境

**位置**：NFR-01（第 4 章）、6.2 节 `web/`

**问题描述**

> NFR-01：系统应当在 **macOS** 与 **Node.js 20 以上**的环境中运行。

Node.js 侧给出了明确的下限（20 以上），而 macOS 侧**没有版本下限**，「macOS」可指 10.13 也可指 26。第 1.2 节的前提是「使用者在**多台** Mac 上工作，各台机器安装的工具与版本不一致」——正是各机器 OS 版本可能不同的状况，因此此处的不明确是实质性的。

更重要的是，**前端的动作环境完全未规定**。NFR-02 要求零第三方依赖，故 `web/app.js` 是无转译的原生 JavaScript，其可用语法直接取决于 Safari 的版本；而 Safari 的版本又由 macOS 版本决定。缺少这项规定，实装时无法判断可否使用 optional chaining、top-level await、`structuredClone` 等特性。

（国际化与可访问性经判断为本项目不必要：利用者仅制作者本人，界面语言单一，且无第三方使用者——不建议追加要件。）

**修改建议**

| ID | 型 | 要件 |

### ISS-25 ｜低｜EARS 合规性｜单条要件内的正反重复

**位置**：NFR-02、SEC-01、SEC-09（第 4・5 章）

**问题描述**

以下三条均在一句内同时给出肯定形与否定形，实为同一约束的两种表述：

- NFR-02「应当**仅**使用 Node.js 标准库实现，**不应当**引入任何第三方运行时依赖」
- SEC-01「应当**仅**将 HTTP 服务绑定至 `127.0.0.1`，**不应当**绑定至 `0.0.0.0` 或任何外部可达地址」
- SEC-09「**不应当**使用 `sudo`，**也不应当**提供任何提权入口」

严格的 EARS 记法要求一条要件对应一个可独立验证的响应。当前形式虽不产生歧义（后半句是前半句的同义反复，非追加约束），但会使测试用例数与要件数的对应关系变得模糊。

**修改建议**

保持现状亦可接受（意图清晰、强调效果有价值）。若追求形式严谨，则简化为肯定形并将否定形移入理由注释，例如 SEC-01 改为「系统应当将 HTTP 服务仅绑定至 `127.0.0.1`。」，其否定形移至既有的理由注释中。**注意 SEC-09 是例外**——「不使用 sudo」与「不提供提权入口」是两个可独立验证的不同约束（前者查命令构造，后者查 UI 与 API），建议拆分为 SEC-09 与 SEC-09b。

### ISS-26 ｜低｜EARS 合规性｜非运行时事件被标为「事件驱动」

**位置**：NFR-03、NFR-09（第 4 章）

**问题描述**

| ID | 型 | 要件 |
|---|---|---|
| NFR-03 | 事件驱动 | 当使用者在新机器上**克隆本仓库**后，系统应当无需执行依赖安装即可启动。 |
| NFR-09 | 事件驱动 | 当**追加新生态**时，系统应当仅通过新增适配器文件与注册来支持该生态……|

EARS 的事件驱动句型前提是「系统能够感知该触发事件并作出响应」。而「克隆仓库」与「追加新生态」都是**开发／运维时的人类行为，系统无从感知**，其「响应」也非运行时行为而是结构性质。NFR-09 的理由注释自身也承认这一点：
> NFR-08、NFR-09 为同一设计方针的两面：前者是**恒常性的结构约束**，后者是**扩展时的可验证条件**。

**修改建议**

型改为「普遍性」并相应调整措辞：

| ID | 型 | 要件 |
|---|---|---|
| NFR-03 | 普遍性 | 系统应当在仅克隆本仓库、未执行任何依赖安装的状态下即可启动。 |
| NFR-09 | 普遍性 | 系统应当使新生态的支持仅通过新增适配器文件与其注册即可完成，不应当要求修改路由层与前端。 |

或者，在第 0 章的记法说明中补一行：「关于开发・扩展时的性质，以普遍性句型记述结构约束，触发条件仅作为可验证条件的文脉提示。」

### ISS-32 ｜低｜歧义｜「拒绝该请求」的未定义

**位置**：SEC-03～SEC-06、SEC-08（第 5 章）

**问题描述**

5 条安全要件均以「则系统应当**拒绝该请求**」结尾，但「拒绝」的具体形态（HTTP 状态码、响应体结构、是否向使用者显示原因）在全文中从未定义。第 8 章的「不静默」原则要求使用者能理解发生了什么，而 SEC-06 本身也附带了提示要求：
> ……并**提示使用者先刷新一览**。

即 SEC-06 需要把「为何被拒」传达到前端，这需要结构化的错误响应——但该结构未定义。同时从安全角度，SEC-03（令牌不正确）不应泄露过多信息，而 SEC-06 则需要具体提示，两者的粒度应有区别，这一点也未规定。

**修改建议**

在第 7 章追加错误响应结构，并在第 5 章冒头追加一段共通规定：

````
### 7.4 错误响应

```js
{ error: 'ITEM_NOT_IN_LIST', message: '条目一览已过期，请先刷新。' }
```

| 要件 | HTTP 状态 | `error` | 备注 |
|---|---|---|---|
| SEC-03 | 401 | `UNAUTHORIZED` | `message` 不含任何细节 |
| SEC-04 | 403 | `FORBIDDEN_ORIGIN` | 同上 |
| SEC-05 | 400 | `UNKNOWN_ACTION` | |
| SEC-06 | 409 | `ITEM_NOT_IN_LIST` | 提示先刷新条目一览 |
| SEC-08 | 400 | `CONFIRMATION_REQUIRED` | |
````

> 第 5 章的共通规定：各要件中的「拒绝该请求」一律指不执行任何子进程，并以 7.4 节所定的错误响应作答。SEC-03 与 SEC-04 的 `message` 不应当含有助于推测令牌或内部状态的信息。

## 总体评价与优先处理建议

### 评价

**优点。** 本文档在同类要件定义书中属于上乘：

- ID 体系严密——49 个 ID 无一跳号、无一重复、无一死引用，附录 A 的件数经实际计数完全正确。这在手写文档中并不常见。
- 模糊词几乎为零——机械检索仅命中 ERR-01 的「摘要」一处。
- 「理由」注释的质量高。FR-02、SEC-01、SEC-04、SEC-07 的注释准确说明了设计判断的依据，对后续维护有实际价值。
- 范围管理意识强。OUT-01～OUT-08 明确区分了「第一版不做」与「永久不做」，这是防范范围膨胀的有效手段。

**弱点。** 问题集中于**第 3～5 章的要件与第 6～7 章的设计之间的接缝**。要件侧描述了「应当做什么」，设计侧描述了「由哪个模块做」，但两者之间的**数据契约**（请求体、返回结构、令牌的流动、生效版本的表达）大面积缺失。ISS-02、ISS-04、ISS-15、ISS-16 都是同一根源的不同表现：第 7 章被当作示意性的接口速写，而非可据以实装的契约定义。这一点必须在进入仕様书前补齐，否则设计阶段会不得不反复回头修改要件。

另一个根源是**第 4 章的配置相关要件（NFR-03、NFR-05）未经与第 5、6 章的对照检查**，导致 ISS-01、ISS-05、ISS-09 三处矛盾与缺口。

### 优先处理顺序

**第 1 波（进入仕様书前必须完成）**

1. **ISS-01** NFR-05 vs SEC-02 的端口矛盾 —— 此项决定 ISS-02 中 URL 告知方式的形态，必须最先裁定。
2. **ISS-02 ＋ ISS-04 ＋ ISS-15 ＋ ISS-16** 第 7 章接口契约的补全 —— 四项应作为一次整体修订实施（令牌流动、ActionRequest、ActionResult、`active` 字段、静态资源端点）。这是最大的一块工作，也是收益最高的一块。
3. **ISS-05 ＋ ISS-09** `.env` 缺失时的行为与配置项默认值表 —— 两项合并处理，一张默认值表即可同时解决。
4. **ISS-03** SEC-04 的 `Origin` 缺失 —— 单条改写即可，成本极低而安全收益明确，应立即处理。
5. **ISS-06** FR-19 的适用范围 —— 需要做出「刷新期间保留旧显示与否」的产品判断，宜尽早裁定。

**第 2 波（同一次修订中一并完成）**

6. **ISS-20** 超时值的用途别区分 —— 影响 `exec.js` 的接口形状，宜与第 1 波的第 7 章修订同期决定。
7. **ISS-10 ＋ ISS-11 ＋ ISS-30** 6.3 节模块表的修正与补全 —— 三项集中于一张表，一并处理效率最高。
8. **ISS-07 ＋ ISS-17** FR-14 的拆分与 FR-18 的删除 —— 涉及重编号，应在同一次修订中完成以免编号混乱。若采纳，附录 A 的件数需同步更新（FR 变为 19－1＋1＝19 或依最终方案重算）。
9. **ISS-13 ＋ ISS-19 ＋ ISS-22 ＋ ISS-23** 要件的追加（NFR-11～NFR-14、FR-15b、FR-20）与手动验证检查清单。
10. **ISS-08、ISS-12、ISS-14、ISS-18、ISS-21** 措辞・用语・引用的修正。其中 ISS-18（「一览」的二义性）涉及全文多处替换，宜在其他修订完成后统一实施以免遗漏。

**第 3 波（有余力时）**

11. ISS-24～ISS-32 的低严重度项。其中 **ISS-32（「拒绝该请求」的未定义）虽列为低，但若在第 1 波实施第 7 章修订时一并加入 7.4 节错误响应表，则几乎不增加成本**，建议提前至第 1 波顺带处理。
